# 登录注册设计

## 1. 阶段 3 的范围与非目标

### 1.1 阶段目标

阶段 3 在阶段 2 用户 CRUD 的基础上，为系统建立完整的登录注册与安全基础。阶段结束后，系统应具备以下能力：

- 通过独立的公开注册接口创建普通用户，并校验 `username`、`phone`、`email` 的唯一性；应用层校验用于提供清晰提示，数据库唯一约束作为并发场景下的最终保障。
- 使用用户名和密码完成登录，密码继续使用 `DelegatingPasswordEncoder` 和 BCrypt 校验，不保存或传输明文密码。
- 登录成功后签发约 15～30 分钟有效的短期 Access Token JWT，并能解析、校验 Token 和获取当前用户。
- 记录登录成功与失败日志，包括用户、结果、IP 和时间，但不记录密码、Token、验证码等敏感信息。
- 先通过最小认证拦截器理解认证流程，再使用 Spring Security 的 `SecurityFilterChain` 完整替换；最终生产代码中不并存两套鉴权逻辑。
- 对认证失败和授权失败分别返回统一格式的 401 和 403 响应，并最终保护现有 `/api/users/**` 接口。
- 支持退出登录、修改密码以及通过邮箱验证码重置密码。
- 使用 `tokenVersion` 控制 Token 失效。退出、修改密码或重置密码后递增用户的 `tokenVersion`，使此前签发的 Token 失效，不以 Token 黑名单作为本阶段主方案。
- 完成 IDEA HTTP Client 接口测试、安全审查、《登录注册设计.md》和《登录安全总结.md》以及阶段验收。

### 1.2 非目标

为控制学习范围，本阶段暂不实现以下功能：

- 完整 RBAC、菜单权限、按钮权限和复杂的角色继承体系。
- Refresh Token、长期会话和多设备会话管理。
- 以 Token 黑名单作为主要失效机制。
- OAuth2、第三方账号登录、单点登录（SSO）和多因素认证（MFA）。
- 前端登录、注册和密码重置页面。
- 管理员查询所有用户登录日志；在没有 RBAC 前，只允许当前用户查看自己的登录日志。

“暂不实现完整 RBAC”不表示所有已登录用户可以访问所有资源。系统仍需执行基础授权，例如阻止用户查看其他用户的登录日志。

## 2. 公开接口、受保护接口和白名单

### 2.1 接口分类

| HTTP 方法 | 路径 | 分类 | 访问者 | 作用 | 关键安全约束 |
|---|---|---|---|---|---|
| `POST` | `/api/auth/register` | 公开 | 匿名用户 | 注册普通用户 | 使用独立注册 DTO；不接收角色、状态等管理字段；校验用户名、手机号和邮箱唯一性 |
| `POST` | `/api/auth/login` | 公开 | 匿名用户 | 校验账号密码并签发 Access Token | 失败响应不得泄露账号是否存在；记录成功或失败日志；不得记录密码和 Token |
| `POST` | `/api/auth/password/reset/request` | 公开 | 匿名用户 | 请求邮箱验证码 | 无论邮箱是否存在都返回相同提示；限制邮箱/IP 频率；生产响应和日志不得包含验证码；数据库只存验证码哈希 |
| `POST` | `/api/auth/password/reset/confirm` | 公开 | 匿名用户 | 校验一次性验证码并重置密码 | 验证码有效期 5～10 分钟；限制失败次数；成功后验证码作废并递增 `tokenVersion` |
| `GET` | `/api/auth/me` | 受保护 | 已认证用户 | 查询当前登录用户 | 只能返回当前用户的非敏感信息 |
| `POST` | `/api/auth/logout` | 受保护 | 已认证用户 | 退出登录 | 递增当前用户的 `tokenVersion`，使旧 Token 失效 |
| `PUT` | `/api/auth/password` | 受保护 | 已认证用户 | 修改当前用户密码 | 校验原密码；新密码必须满足强度要求；成功后递增 `tokenVersion` |
| `GET` | `/api/login-logs/me` | 受保护 | 已认证用户 | 查询当前用户自己的登录日志 | 用户身份从认证上下文取得，不接受任意用户 ID 代查 |
| 所有方法 | `/api/users/**` | 受保护 | 已认证且通过授权的用户 | 用户后台管理 | 阶段 3 必须完成认证保护；具体管理员 RBAC 留待后续阶段 |
| 所有方法 | 其他未明确公开的接口 | 默认受保护 | 已认证用户 | 避免新增接口被意外匿名访问 | 采用“默认拒绝匿名、按需精确放行”的策略 |

公开接口只表示调用前不要求持有 Access Token，不表示接口没有安全控制。注册、登录和重置密码仍必须进行参数校验、频率限制、防账户枚举和敏感信息保护。

### 2.2 Spring Security 白名单

白名单应尽量使用“HTTP 方法 + 精确路径”，避免因路径范围过大而放行受保护接口。

| HTTP 方法 | 路径 | 生效环境 | 放行原因 |
|---|---|---|---|
| `POST` | `/api/auth/register` | 全部 | 匿名用户需要注册 |
| `POST` | `/api/auth/login` | 全部 | 匿名用户需要登录 |
| `POST` | `/api/auth/password/reset/request` | 全部 | 未登录用户需要申请重置密码 |
| `POST` | `/api/auth/password/reset/confirm` | 全部 | 未登录用户需要确认验证码并重置密码 |
| `GET` | `/swagger-ui/**` | 仅开发环境 | 访问 Swagger UI 及其静态资源 |
| `GET` | `/v3/api-docs/**` | 仅开发环境 | Swagger UI 获取 OpenAPI 文档 |

不得直接放行 `/api/auth/**`。虽然注册、登录和忘记密码位于该前缀下，但当前用户、退出和修改密码接口同样位于该前缀下；宽泛放行会使这些本应受保护的接口变成匿名接口。

若后续前端跨域访问确实需要 CORS 预检，再单独处理 `OPTIONS` 请求。`OPTIONS /**` 不是业务接口，也不应在没有实际需求时提前加入生产白名单。

## 3. 认证、授权、401 与 403

认证和授权解决的是两个不同问题，并且具有先后顺序：系统必须先确认请求者是谁，才能判断其是否有权执行某项操作。

| 概念 | 核心问题 | 发生阶段 | 本项目示例 |
|---|---|---|---|
| 认证（Authentication） | 你是谁？ | 先执行 | 登录时校验账号密码；请求到达时解析并校验 JWT |
| 授权（Authorization） | 你能做什么？ | 认证成功后执行 | 判断当前用户是否能查看某条登录日志或访问后台用户管理接口 |
| `401 Unauthorized` | 系统为什么无法确认你的有效身份？ | 认证失败 | Token 缺失、格式错误、签名错误、已过期或 `tokenVersion` 不匹配 |
| `403 Forbidden` | 身份已经确认，为什么仍不允许访问？ | 授权失败 | 已登录用户尝试查看其他用户的登录日志 |

`401 Unauthorized` 的名称容易使人误解，它在 HTTP 安全语义中更接近“未通过认证”。重新登录并取得有效 Token 通常可以解决 401，但不能解决权限不足导致的 403。

本项目中的典型状态码边界如下：

- 未携带 Token 访问 `/api/users/**`：返回 401。
- 携带伪造、过期或因 `tokenVersion` 变化而失效的 Token：返回 401。
- 登录时账号或密码错误：凭据认证失败，返回 401，同时使用统一提示避免暴露账号是否存在。
- 已认证用户尝试查看他人的登录日志：返回 403。
- 注册请求参数格式错误：返回 400，而不是 401 或 403。
- 注册时用户名、手机号或邮箱发生唯一性冲突：返回 409，而不是 401 或 403。

无论是 401 还是 403，都应通过 Spring Security 的统一处理入口转换为项目现有的 `Result<T>` 响应格式，不能返回默认 HTML 错误页。

## 4. 注册接口为何不能复用后台创建用户接口

公开注册和后台创建用户虽然最终都会向 `sys_user` 写入数据，但它们不是同一个业务用例，不能共用对外接口和请求 DTO。

首先，两者的信任边界不同。`POST /api/auth/register` 面向匿名且不可信的外部用户；`POST /api/users` 属于后台管理能力，最终应只允许经过认证和授权的管理人员调用。直接把后台创建接口放入白名单，会同时放开其中所有管理能力。

其次，两者允许客户端提交的字段不同。公开注册只能接收注册所需的 `username`、`password`、`phone`、`email` 等字段，不能接收 `status`、`role`、`tokenVersion`、`deleted` 等管理或安全字段。否则攻击者可能利用批量赋值主动启用账号、指定高权限角色或操纵安全状态。

再次，管理字段的默认值必须由服务端根据注册策略设置。即使当前后台创建 DTO 尚未包含角色字段，也不能因此复用；未来后台 DTO 增加管理字段时，复用会在没有明显代码错误的情况下扩大公开接口的攻击面。

最后，两类业务规则会独立演进。公开注册可能逐步增加验证码、IP/账号频率限制、防机器人和防账户枚举；后台创建用户可能增加管理员审计、角色分配、初始状态和通知流程。独立的路径和 DTO 可以使两种业务的变更互不扩大对方的风险范围。

因此，公开注册固定使用独立的 `POST /api/auth/register` 和注册请求 DTO。注册时必须在应用层校验 `username`、`phone`、`email` 唯一性，并由数据库唯一约束提供最终保障。

不复用对外接口和 DTO，并不意味着底层实现必须全部复制。密码哈希、唯一性检查、Mapper 操作以及安全且通用的内部服务能力可以复用，但调用入口、可接收字段和业务规则必须保持清晰隔离。

## 5. Access Token JWT 设计

### 5.1 Token 用途

登录成功后，服务端签发一个短期 Access Token。客户端后续访问受保护接口时，在请求头中携带：

```text
Authorization: Bearer <access-token>
```

服务端收到请求后解析 Token，验证签名、过期时间和用户安全状态，然后把当前用户身份放入认证上下文。后续 Controller 或 Service 不再依赖客户端传入的用户 ID 来判断当前用户是谁。

### 5.2 Token 有效期

本阶段使用短期 Access Token，有效期控制在 15～30 分钟。短有效期可以降低 Token 泄露后的风险窗口。

本阶段暂不实现 Refresh Token，因此 Token 过期后用户需要重新登录。Refresh Token、长期会话、多设备会话管理属于后续阶段内容。

### 5.3 Token 中保存的内容

JWT 只保存识别当前用户和校验 Token 状态所需的最小信息：

| Claim | 含义 | 说明 |
|---|---|---|
| `sub` | Subject，用户 ID | 用于定位当前登录用户 |
| `username` | 登录用户名 | 便于日志或调试识别，但不能只依赖它做数据库定位 |
| `tokenVersion` | Token 版本号 | 与数据库 `sys_user.token_version` 比较，用于判断 Token 是否已失效 |
| `iat` | 签发时间 | 判断 Token 是何时生成的 |
| `exp` | 过期时间 | 超过该时间后 Token 无效 |

Token 中不得保存密码哈希、手机号、邮箱、验证码、权限以外的敏感资料。JWT 内容默认只是 Base64Url 编码，不是加密；任何拿到 Token 的人都可以解码查看其中的 Claim。

### 5.4 tokenVersion 失效机制

本阶段不使用 Token 黑名单作为主方案，而使用 `tokenVersion` 控制旧 Token 失效。

签发 Token 时，将当前用户表中的 `token_version` 写入 JWT 的 `tokenVersion` Claim。后续请求到达时，服务端需要：

1. 校验 Token 签名是否合法。
2. 校验 Token 是否过期。
3. 根据 `sub` 查询当前用户。
4. 比较 JWT 中的 `tokenVersion` 与数据库中的 `token_version` 是否一致。

如果不一致，说明该 Token 是旧 Token，应返回 401。

以下操作成功后必须递增数据库中的 `token_version`：

- 退出登录。
- 修改密码。
- 邮箱验证码重置密码。

递增后，旧 Token 即使没有过期，也会因为版本号不匹配而失效。

### 5.5 认证失败边界

JWT 校验失败属于认证失败，统一返回 401，包括：

- 未携带 `Authorization` 请求头。
- 请求头不是 `Bearer <token>` 格式。
- Token 签名错误。
- Token 已过期。
- Token 中的用户不存在、被禁用或已删除。
- JWT `tokenVersion` 与数据库 `token_version` 不一致。

这些失败都不应该返回默认 HTML 错误页，也不应该把 Token、密钥或异常堆栈暴露给客户端。
